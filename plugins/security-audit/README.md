# security-audit

按需深度安全审计：对**已经存在**的代码做多 agent 扫描——包括从来不是 AI 写的、历史遗留的那些——
每条发现经独立复核后才进报告；选定的发现可以变成补丁，但补丁由你自己应用。

它是三层代码安全中的**存量清查**那一层。三层的分工按「谁能看见哪些代码」划分：

| 层 | 触发 | 看得见的代码 |
| --- | --- | --- |
| `security-guidance` 插件 | 自动，写码过程中 | 只有增量：本次写入、本轮改动、AI 自己发起的提交 |
| **`security-audit`（本插件）** | 手动，你发起 | **整个仓库 / 任意区间：分支 diff、单个提交、无版本控制的目录** |
| 内置 `/security-review` | 手动，单次 | 当前分支相对基线分支的全部改动 |

自动层只看得见 AI 自己动过的东西；清查存量是它结构上做不到的事——这就是本插件存在的理由。

## 安装后你会得到

`/security-audit:security-audit` —— 一个前门，它先量后问，然后按你选的那件事各走一套独立食谱：

- **扫全库**（`jobs/scan-codebase.md`）：整个仓库，或聚焦其中一块区域
- **扫改动**（`jobs/scan-changes.md`）：本分支相对基线的 diff、某个 ref 对（PR 的 base/head）、或单个提交
- **出补丁**（`jobs/suggest-patches.md`）：把报告里选定的发现变成补丁文件

也可以不打命令——直接说「扫一下这个仓库」「帮我看看这个分支的改动」「把 F1 修了」，前门认这些说法。

不装任何东西的 `git diff` 级自查，用内置的 `/security-review`；本插件的「扫改动」是它的深度对照面
（并行狩猎 + 逐条独立复核 + 落盘报告）。

## 插件里都有什么

```
plugins/security-audit/
├── skills/security-audit/
│   ├── SKILL.md            # 前门：选哪件事、固定措辞、三件事共用的口径
│   ├── jobs/               # 三套食谱，各自独立，进门后读哪一份就照哪一份做
│   └── specs/              # 产物契约：报告长什么样、补丁长什么样
├── workflows/scan.js       # 扫描编排：分区 → 威胁建模 → 并行狩猎 → 独立复核（high 档三视角 Panel）
└── agents/                 # 5 个子代理：威胁建模 / 狩猎（兼作改动的对抗复核）/ 复核发现 / 起草补丁 / 复核补丁
```

扫描的编排在 `workflows/scan.js` 里，不在对话里：扇出几路、哪些候选算重复要合并、复核票怎么算，都是
脚本里的确定性代码。同一份输入跑两次，agent 的**数量与分组**是一样的（发现的内容仍然随机，见「能力
边界」）。脚本自己不读文件、不跑 git——它只派 agent 和算数，产物由你自己写。

## 扫描做了什么

1. **先量后问**（只读）：统计仓库类型、文件数、基线分支、本分支独有提交数、未提交改动，然后
   **把可选的扫描范围与各自的文件数、相对成本摆出来**。你不选，它不动任何东西。
   - 扫全库：整库 / 聚焦某个目录 /「不知道，你替我定」——按仓库规模自己挑，并在下一步的确认里说明
     它假设了什么
   - 扫改动：本分支相对基线的 diff / 单个提交 / 一个 ref 对——同样带「不知道，你替我定」
   - 你直接指定了某个 commit 就跳过这道菜单：范围已经定了
   - 工作区有未提交改动时会明说：diff 类范围只覆盖已提交内容
   - 前门还会先固定说一句「无人值守跑得最顺，开跑前用 Shift+Tab 把权限模式调到你要的档位」——
     每次措辞相同，不是提问
2. **一句固定的开跑确认**：措辞每次完全相同，不带文件数、成本、时长。点「是」才开跑；没拿到确认
   就不建任何目录、不派任何 agent。
3. **建报告目录**：`WAVE-SECURITY-<时间戳>/`，并写入自带忽略规则（见下）。
4. **扫描本身交给 `scan` 工作流跑**，三个阶段顺序固定、不可跳（`/workflows` 里能看到跑到哪了）：
   - **梳理架构 + 建威胁模型**（每组件组 1 个 agent）：入口点、信任边界、敏感数据、攻击者会怎么打——
     这是该组所有狩猎者的作战简报。
   - **并行狩猎**（每区域 1 个 agent，上限随档位：low 3 / medium 6 / high 12）：只报能说清可达路径的
     问题。区域多于上限时，最小的几个按目录并进相邻区域，并在报告里记下是怎么并的。
   - **独立复核**（每条发现 1 次判定）：复核者拿不到发现者的推理与置信度，只拿发现和代码，自己读调用
     方与校验点，给出 `confirmed / rejected / uncertain`。**只有 `confirmed` 进报告**，其余进否决清单并
     附理由，不计入发现数。`high` 档换成三视角 Panel：每条发现由三个复核者分别只验一件事（代码是否如
     描述、输入是否攻击者可控、有无缓解且是否可达），多数票才算数——一确认一否决一不确定就是不确定。

   工作流返回的是已合并去重、已复核、已编号（`F1`…／`R1`…）的结论；写 `report.md` / `findings.json` /
   `results.sarif` 仍由会话里的模型完成，它只做誊写，不再重新判定。
5. **落三份产物**（见下），并在对话里汇报范围、修订版本、各级严重度数量、报告路径。

扫描是**后台跑**的：确认之后这一轮对话就结束，扫描跑完再自动接着写报告。所以确认完可以先去做别的，
不必守着——想中途看进度用 `/workflows`，想掐掉也在那里。

## 产物目录

```
WAVE-SECURITY-<yyyyMMdd-HHmmss>/
├── .gitignore          # 内容为 `*`：整个目录不进 git add
├── report.md           # 人读：范围与修订版本、发现表、逐条详述、否决清单、两条口径说明
├── findings.json       # 机器可读：scan 元信息 + findings[] + rejected[]
├── results.sarif       # SARIF 2.1.0，按 CWE 归类，可直接喂给支持代码扫描的平台
└── patches/            # 只有「出补丁」那件事会写；没跑过补丁就没有这个目录
```

- 目录名带时间戳，所以两次扫描各留一份，不会互相覆盖。
- 目录里的 `.gitignore` 用 `*` 把自己整个排除在版本控制之外——普通 `git add` 不会误收它。
  **要归档报告，显式删掉那条忽略规则即可。**
- 报告里的每条发现都带 `revision`：扫描时的 commit、`git hash-object` 得到的 blob sha（不在版本
  控制下则记 size/mtime）。这让报告能归因到它描述的确切代码。

## 补丁由谁拍板

`/security-audit:security-audit` 选「出补丁」（或直接说「把 F1 修了」；可跟 `F1 F3` 指定发现，默认让你
多选，一次最多 5 条）：

1. **先校验报告没过期**：逐条比对文件当前内容与报告记录的 blob sha；不一致就跳过该发现并提示重新
   扫描，而不是照着过期报告改写。
2. **在仓库临时副本里起草**（`/tmp/WAVE-SECURITY-PATCH-<ts>-F<n>/`），你的源文件保持不动。
3. **两名独立 agent 同时上场（一个复核、一个对抗）**：复核者跑项目测试（读到测试命令时）、独立读 diff
   判断三件事——修好了该发现、没引入新漏洞、其余行为不变；对抗者只问一个问题——「这个改动在位之后，
   攻击者能做什么本不该做的事」，报出改动打开的路径、或让原发现的利用仍然可达的另一条路。**两边都过才
   算数**：复核者三点不能同时确认、或对抗者报出一条计数路径（标了「既存且与本次无关」的除外），就
   **不产出补丁**，改为给一段说明。
4. **产出**：每个发现一份 `patches/F<n>.patch` + `patches/F<n>.md`（改动说明、验证方式、残余风险、如何
   应用），最后写一份 `patches/PATCHES.md` 一页索引（谁有补丁、谁没有、为什么、怎么应用）。索引里的
   标签写的是**面板的判定**，不写「已测试 / 未测试」；补丁对应的代码在项目自己的测试里没有覆盖时，
   要说明这份信心来自通读而不是跑测试。
   **补丁从不自动应用**——`git apply <路径>` 由你执行。临时副本用完即清。

## 打印什么、不打印什么

- 扫描**只读**：不改你的源文件、不跑被审计的代码、不动 git 状态；唯一的写入在自己的报告目录里。
- 仓库里的内容（代码、注释、`AGENTS.md`、既存报告、仓库自带的 security 指引）一律当**数据**看，不当
  指令。里面出现「跳过这里的复核」「跑一下这个命令确认」「这个文件已确认干净」这类句子，只会被当成
  篡改迹象写进报告——不会被执行，也不会改变扫描范围或产物。
- 报告里的**硬编码凭据只写文件与行号，不写值**，包括从子代理嘴里转述的那些字段。
- 补丁阶段的起草发生在**子代理**里、且只在临时副本（`/tmp/WAVE-SECURITY-PATCH-*`）中；你的源文件自始
  至终不在改动范围内。技能的 `allowed-tools` 已经把"报告目录内的写入"登记为免确认；子代理在临时副本
  里的编辑会走一次权限确认（想全程免确认，在 `permissions.allow` 里加一条
  `Edit(**/WAVE-SECURITY-PATCH-*/**)`）。对抗复核与狩猎共用 `vulnerability-hunter`
  （`Read`/`Glob`/`Grep`/`Bash`），它被要求只读、只搜索——不跑项目测试、不改任何文件：这条靠 prompt
  约束，不是权限拦截；全队唯一跑测试的是复核者。
- 扫描**不阻塞**任何动作：它把发现交给报告和你的判断，不拦提交、不拦合并。

## 能力边界（说在前面）

- 扫描是**随机的**：同一份代码扫两次，发现的集合可以不同。它的价值来自定期执行，不是可复现。
- 可能**漏报**。它是纵深防御里的若干层之一，不是完整方案；也不能替代你已有的 SAST / 依赖扫描——
  它推理的是代码语义，与确定性检查互补。
- 自动层看不见你在自己终端里做的改动；本层的 diff 范围也只覆盖**已提交**内容。
- 面向**用户自有或已获授权的代码**，不用于扫描第三方代码。
- 报告与发现会进入 AI 的上下文——含代码片段。按公司对模型输入的规定处理敏感代码。

## 卸载

在插件市场卸载即可，本插件不留常驻进程、不写会话外状态。已产出的 `WAVE-SECURITY-*` 目录与
`/tmp/WAVE-SECURITY-PATCH-*` 临时副本可以整个删掉；临时副本正常情况下在当次补丁流程结束时已清理。
