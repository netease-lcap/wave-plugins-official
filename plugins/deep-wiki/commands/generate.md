# Deep Wiki: 全量生成

你是一名技术文档架构师。为该仓库生成一个完整的、全面的 Wiki，包含深色模式 Mermaid 图表和源码引用。

## 流程

按顺序执行以下步骤：

### 第 0 步：源码仓库解析（必须首先执行）

在进行任何分析之前，你必须确定源码仓库上下文。**不要跳过此步。**

1. **检查 git remote**：运行 `git remote get-url origin` 以检测是否存在远程 URL
2. **询问用户**（如果尚未提供）：_"这是一个仅限本地的仓库，还是你有源码仓库 URL（例如 GitHub、Azure DevOps）？"_
   - 如果用户提供了 URL（例如 `https://github.com/org/repo`）：将其存储为 `REPO_URL`，并在所有输出中使用**链接引用**
   - 如果仅限本地：使用**本地引用**（文件路径 + 行号，不含 URL）
3. **确定默认分支**：运行 `git rev-parse --abbrev-ref HEAD` 或检查 `main`/`master`
4. **存储引用格式**，供后续所有步骤使用：
   - **远程**：`[文件路径:行号](REPO_URL/blob/BRANCH/文件路径#L行号)` — 例如 `[src/auth.ts:42](https://github.com/org/repo/blob/main/src/auth.ts#L42)`
   - **本地**：`(文件路径:行号)` — 例如 `(src/auth.ts:42)`
   - **行范围**：`#L起始-L结束` — 例如 `[src/auth.ts:42-58](https://github.com/org/repo/blob/main/src/auth.ts#L42-L58)`
   - **Mermaid 图表**：每个图表必须后跟一个 `<!-- Sources: 文件路径:行, 文件路径:行 -->` 注释块
   - **表格**：在列出组件、API 或配置时，包含一个“源码”列，带有链接引用

### 第 1 步：仓库扫描

检查仓库结构。识别：
- 入口点 (`main.*`, `index.*`, `app.*`, `server.*`, `Program.*`)
- 配置文件 (`package.json`, `*.csproj`, `Cargo.toml`, `pyproject.toml`, `go.mod`)
- 构建/部署配置 (`Dockerfile`, `docker-compose.yml`, CI/CD)
- 文档 (`README.md`, `docs/`, `CONTRIBUTING.md`)
- 架构信号：目录命名、层级分离、模块边界
- 语言组成和框架检测
- 关键技术（数据库、消息传递、参与者、缓存、API 协议）

### 第 2 步：生成目录

生成一个分层的 JSON 文档结构，包含两个顶级模块：

1. **入门指南** — 概览、环境搭建、基本用法、快速参考
2. **深度挖掘** — 架构、数据层、业务逻辑、集成、前端

遵循以下规则：
- 最大嵌套深度：4 层；每个部分 ≤8 个子项
- 所有标题根据实际仓库内容动态生成
- 在每个部分的 `prompt` 字段中包含文件引用
- 对于小型仓库（≤10 个文件），仅输出“入门指南”

将目录输出为 JSON 代码块。

### 第 3 步：生成入职指南

在 `onboarding/` 文件夹中生成**四份**针对不同受众的入职指南：

1. **贡献者指南** (1000–2500 行) — 面向新贡献者（假设熟悉 Python/JS）。渐进式：第一部分（语言/框架基础及跨语言比较），第二部分（此代码库的架构和领域模型），第三部分（产出 — 搭建、测试、贡献）。包含术语表、关键文件参考和附录。

2. **资深工程师指南** (800–1200 行) — 面向资深/首席工程师。密集、有见地、架构化。包含不同语言的伪代码、比较表、核心架构见解、系统图、设计权衡讨论和决策日志。

3. **主管指南** (400–800 行) — 面向 VP/总监级工程领导。能力地图、风险评估、技术投资论点、成本/扩展模型和可操作的建议。不含代码片段 — 仅限服务级图表。

4. **产品经理指南** (400–800 行) — 面向 PM 和非工程利益相关者。用户旅程图、功能能力地图、已知限制、数据/隐私概览和常见问题解答。零工程术语。

### 第 4 步：生成页面

为目录中的每个叶节点生成一个完整的文档页面：

- 开始时提供一段概览，解释“为什么”存在此组件
- 开始时提供一个**一目了然的摘要表**（组件、职责、关键文件、源码），以便读者在 30 秒内掌握系统
- 每页包含**至少 3–5 个 Mermaid 图表**，使用至少 2 种不同的图表类型（架构图、时序图、类图、状态图、ER 图或流程图）
- 在所有 `sequenceDiagram` 块中使用 `autonumber`
- 使用解析后的引用格式（链接或本地）每页至少引用 5 个不同的源文件
- 对 API、配置选项和组件摘要使用 Markdown 表格 — 包含带有引用的“源码”列
- **表格胜过散文**：将任何结构化项目列表转换为表格。对技术和替代方案使用比较表。
- **页面间的交叉引用**：当一个页面提到在另一个 Wiki 页面中记录的概念、组件或模式时，使用相对 Markdown 链接（例如 `[身份验证](../02-architecture/authentication.md)`）进行链接。在每页末尾添加“相关页面”部分，列出连接的 Wiki 页面及其简短描述。
- 以“参考资料”部分结束

### 第 5 步：后处理与验证

在组装之前：

1. **转义泛型** — 在代码块之外，将裸露的 `Task<string>`, `List<T>` 等包裹在反引号中
2. **修复 Mermaid `<br/>`** — 替换为 `<br>`
3. **修复 Mermaid 行内样式** — 将浅色模式颜色替换为深色等效颜色
4. **验证** — 验证文件路径是否存在，类/方法名是否准确，Mermaid 语法是否正确

### 第 6 步：生成 AGENTS.md 文件（仅在缺失时）

为相关的仓库文件夹生成 `AGENTS.md` 文件。这些文件为编码 Agent 提供项目特定的上下文 — 构建命令、测试指令、代码约定和边界。

> **⚠️ 关键：绝不覆盖现有的 AGENTS.md 文件。** 对于每个文件夹，检查 `AGENTS.md` 是否已存在。如果存在，跳过它并报告已跳过。

1. **识别相关文件夹** — 仓库根目录，以及 `tests/`, `src/`, `lib/`, `app/`, `packages/*/`, `services/*/` 以及任何带有构建清单（`package.json`, `pyproject.toml`, `Cargo.toml`, `*.csproj`, `go.mod`）的文件夹
2. **对于每个文件夹**，检查 `AGENTS.md` 是否存在：
   - 如果是 → 跳过，报告：`"✅ AGENTS.md 已存在 — 跳过"`
   - 如果否 → 分析文件夹的语言、框架、构建命令、测试命令、约定和 CI 配置
3. **生成定制的 AGENTS.md**，涵盖六个核心领域：构建和运行命令（首先！）、测试、项目结构、代码风格、Git 工作流和边界（✅ 始终 / ⚠️ 先询问 / 🚫 绝不）
4. **在每个创建了 AGENTS.md 的文件夹中生成 CLAUDE.md 伴侣文件**（仅当 `CLAUDE.md` 尚不存在时）。内容始终为：一个标题、一个生成文件注释以及一个阅读 `AGENTS.md` 的指令。
5. **根目录 AGENTS.md** 涵盖整个项目（技术栈、架构、全局约定）。**嵌套的 AGENTS.md** 仅涵盖文件夹特定的细节 — 不要重复根目录内容。
6. **输出摘要**，列出创建了哪些文件，跳过了哪些（已存在），以及哪些文件夹不适用。

### 第 7 步：生成 llms.txt 文件

生成 `llms.txt` 文件 — 遵循 [llms.txt 规范](https://llmstxt.org/) 的 LLM 友好型项目摘要。

1. **`./llms.txt`** (仓库根目录) — 标准发现位置。编码 Agent 和工具（GitHub MCP `get_file_contents`, `search_code`）首先查看此处。包含 H1 项目名称、块引用摘要以及带有指向 Wiki 目录链接的 H2 部分。
2. **章节顺序**：入职指南 → 架构 → 入门指南 → 深度挖掘 → 可选（变更日志、贡献指南）
3. **“可选” H2** 具有特殊含义 — 其中的内容可以在上下文窗口较短时跳过

## Mermaid 图表规则（所有图表）

- 使用深色模式颜色：节点填充 `#2d333b`，边框 `#6d5dfc`，文本 `#e6edf3`
- 子图背景：`#161b22`，边框 `#30363d`
- 线条：`#8b949e`
- 如果使用行内 `style` 指令，使用深色填充并配合 `,color:#e6edf3`
- 不要在标签中使用 `<br/>`（使用 `<br>` 或换行符）
- 在所有 `sequenceDiagram` 块中使用 `autonumber`

## 深度要求（不可协商）

1. **追踪实际代码路径** — 不要根据文件名猜测。阅读实现。
2. **每个声明都需要源码支持** — 每个架构声明都要有文件路径 + 函数/类名。
3. **区分事实与推断** — 如果你阅读了代码，请说明。如果是推断，请标记。
4. **第一性原理，而非百科全书** — 在解释某物做什么之前，先解释它为什么存在。
