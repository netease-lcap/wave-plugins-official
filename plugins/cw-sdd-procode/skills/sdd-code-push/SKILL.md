# sdd-code-push 工作流

用于代码项目的分支化开发与仓库同步：开发工具打开项目后连接到开发分支，默认在独立 worktree 中工作；开发完成后依次推送开发分支、合并到 `master` 并推送，最后输出仓库同步提示。

本 skill 不绑定具体开发工具或 CLI。工具名称、命令、分支名、远端和推送方式都必须从项目配置、工具帮助或用户确认中获得，禁止臆造。

## 核心原则

- 先发现工具、项目、开发分支、远端和推送方式，再执行任何写操作。
- 推送前必须确认推送范围：仅推送当前分支，或推送当前分支并合并到 master。
- 需要用户确认时，优先使用 Ask User Question / `request_user_input` 工具发起结构化选择，不自行假设。
- 默认使用独立 worktree，不在主工作区直接开发。
- 开发阶段只操作开发分支，不向 `main`、`master`、`release` 等分支提交或推送。
- 开发分支推送并核验成功后，按第 6 步合并到 `master` 并推送；除此之外不向其他分支推送。
- 所有代码变更通过 Git 或开发工具的标准推送流程提交，不手工修改工具生成的中间文件。
- 推送前必须核对差异、运行校验，并确认目标分支与远端。
- 禁止 force push、禁止改写已推送历史、禁止覆盖他人提交。
- 推送完成后必须核验远端结果，不能只看本地命令退出码。
- 按推送范围在回复末尾输出对应提示：仅当前分支为 `> **当前分支已推送。**`；合并 master 为 `> **git仓库已同步。**`

## 参数发现

开始时先确认以下信息；能自动识别的注明依据，不能识别的询问用户：

- 开发工具或 CLI 名称、版本、帮助入口；
- 项目根目录与项目标识；
- Git 仓库地址与远端名称；
- 开发分支与 `master` 分支的准确名称；
- 合并到 `master` 的方式、合并策略与分支保护规则；
- worktree 根目录与工具的默认 worktree 行为；
- 工具生成文件与构建产物的存放位置和生成方式；
- 开发分支推送与 `master` 合并的准确命令、API 或界面操作；
- 推送范围：仅当前分支，或当前分支并合并到 `master`；
- 构建、预览、测试或校验命令；
- 认证方式与凭据来源。

如果「推送」可能指以下任一含义，必须先向用户确认：

1. `git push` 源码到开发分支；
2. 通过开发工具同步本地变更到远端；
3. 两者都要，且存在固定先后顺序。

## 第 0 步：确认推送范围

在任何推送操作之前，使用 Ask User Question 询问用户本次「推送」的范围：

- `仅推送当前分支 (Recommended)`：只把当前开发分支推送到远端，不合并、不推送 `master`。
- `推送当前分支并合并到 master`：先推送当前开发分支，再合并并推送 `master`。

记录用户选择；未确认推送范围前不得提交、推送或合并。

## 第 1 步：预检

在任何创建 worktree、提交或推送之前：

1. 确认仓库状态：当前分支、未提交改动、未跟踪文件、现有 worktree 列表。
2. 确认远端可访问，拉取最新开发分支信息。
3. 确认目标开发分支存在，且不是受保护分支。
4. 确认工作区没有会被覆盖的未提交改动。
5. 确认工具版本支持当前项目的 worktree 与分支推送能力。
6. 输出预检表：

   | 项目 | 值 | 依据 |
   | --- | --- | --- |
   | 开发工具/CLI |  |  |
   | 项目路径 |  |  |
   | 开发分支 |  |  |
   | master 分支 |  |  |
   | 远端 |  |  |
   | worktree 路径 |  |  |
   | 推送范围 |  |  |
   | 推送方式 |  |  |
   | 合并到 master 方式 |  |  |
   | master 推送权限 |  |  |
   | 校验命令 |  |  |

预检不通过时停止，不得继续创建 worktree 或推送。

## 第 2 步：连接开发分支并准备 worktree

优先使用开发工具自带的项目打开、分支切换和 worktree 创建能力。

### 工具默认开启 worktree

- 验证工具创建的 worktree 是否位于预期目录、是否基于正确的开发分支、是否指向正确远端。
- 如果项目已经在 worktree 中打开，复用该 worktree，不要重复创建或嵌套创建。
- 如果 worktree 已存在但分支不对、基线过期或存在未提交改动，停止并询问用户。
- 一个 worktree 只服务一个开发分支和一个任务范围。

### 工具未自动创建 worktree

先查看工具是否提供 worktree 参数或配置。没有可用能力时，才考虑使用 Git 原生命令，并先向用户确认。

创建 worktree 时必须：

- 基于最新的开发分支；
- 使用新的独立目录；
- 不在主工作区切换分支；
- 记录 worktree 路径、分支名和基线提交。

### 环境准备

在 worktree 内完成依赖安装、配置初始化和工具登录态检查。不要把主工作区的构建产物、缓存或本地配置直接复制进来，除非项目文档明确要求。

## 第 3 步：在 worktree 中开发

- 所有代码、配置和生成变更都发生在 worktree 内。
- 页面、逻辑、数据模型等变更优先通过开发工具完成。
- 不手工编辑工具生成的中间文件；确需修改生成文件时，先确认工具是否支持，并记录原因。
- 保持变更范围聚焦，不提交与当前任务无关的文件。
- 按仓库现有约定进行小步提交；提交信息说明业务目的，不写无意义占位。
- 开发过程中定期运行构建、预览、测试或校验命令。

## 第 4 步：推送前核对

推送前必须完成：

1. 查看工作区状态与差异，确认只包含预期变更。
2. 检查是否混入密钥、令牌、个人配置、构建产物、日志或临时文件。
3. 确认工具生成的代码、配置或产物已正确更新，且与源码变更一致。
4. 拉取最新开发分支，按仓库约定合并或变基；解决冲突后重新校验。
5. 运行项目要求的构建、测试、预览或校验。
6. 如工具支持推送预检、差异预览或 dry-run，先执行。
7. 输出推送前摘要：

   - 目标分支与远端；
   - 将推送的提交或变更；
   - 变更文件与影响范围；
   - 校验结果；
   - 已知风险与回滚方式。

如推送会覆盖共享环境、触发自动部署、改写远端历史或影响他人分支，必须先获得用户确认。

## 第 5 步：推送代码到开发分支

严格按工具文档规定的顺序执行。常见顺序是：提交源码 → 推送开发分支；但必须以实际工具要求为准。

### 源码推送

- 推送到已确认的开发分支，不使用 force。
- 不直接推送到受保护分支。
- 推送被拒绝时，先拉取并解决差异，再重新校验和推送。

### 推送后核验

- 确认远端开发分支包含预期提交。
- 如存在 CI/CD，检查构建或部署状态。
- 核验失败时停止，不得用重复 force push 或删除远端分支解决。

开发分支推送并核验成功后：

- 若选择「仅推送当前分支」，直接进入第 7 步；
- 若选择「推送当前分支并合并到 master」，继续执行第 6 步。

## 第 6 步：合并到 master 并推送

本步骤仅在用户选择「推送当前分支并合并到 master」时执行。

前置条件：第 5 步的开发分支推送已成功并完成核验；当前没有未提交改动；`master` 分支存在且远端可访问。

1. 拉取最新的 `origin/master`，确认本地与远端的基线。
2. 优先使用开发工具提供的合并或同步到 `master` 的能力。工具没有该能力时，使用 Git 在独立 worktree 或临时分支中执行合并，避免切换开发 worktree。
3. 把开发分支合并到 `master`。优先 fast-forward；不能 fast-forward 时按仓库约定创建合并提交。不要强制覆盖远端历史。
4. 出现冲突时停止，不自行选择冲突解决方案；向用户说明冲突文件、冲突原因与可选处理方式。
5. 在合并后的 `master` 上重新运行构建、测试或校验。
6. 推送 `master` 到远端，不使用 force。若 `master` 受保护或禁止直接推送，停止并询问，不得绕过保护规则。
7. 核验远端 `master` 已包含开发分支的提交。
8. 合并、校验、推送和核验全部成功后，记录成功状态并进入第 7 步；不要在此时输出最终提示。

仅合并模式下，未完成第 6 步或任一步核验失败时，不得输出第 7 步的合并提示。

## 第 7 步：收尾与最终提示

向用户汇报：

- 开发分支与远端；
- `master` 分支与远端（仅合并模式）；
- worktree 路径；
- 提交哈希；
- 开发分支推送结果；
- `master` 合并与推送结果（仅合并模式）；
- 变更摘要与校验结果；
- 未完成项、风险和后续建议。

全部汇报内容输出完毕后，根据第 0 步的推送范围，在整条回复的最末尾单独输出对应高亮提示块，且只输出一次。

仅推送当前分支时输出：

> **当前分支已推送。**

推送当前分支并合并到 master 时输出：

> **git仓库已同步。**

输出要求：

- 使用 Markdown 引用块 + 粗体实现高亮；如果当前界面支持专用高亮或提示块，优先使用专用块。
- 提示内容必须与本次推送范围一致，不得混用两种提示。
- 该提示必须是整条回复的最后内容，前后留空行，不得混入汇报列表。
- 一次流程只输出一次，不得重复输出。
- 任一步失败或核验未通过时，不得输出该提示块。

worktree 默认保留，直到用户确认变更已推送且不需要继续开发。清理时：

- 先确认没有未提交改动；
- 使用工具或 Git 的非强制方式移除；
- 不删除远端分支，不删除历史提交；
- 清理失败时保留现场并说明原因。

## 必须停下来询问用户的情况

- 无法确定开发工具、项目根目录或开发分支；
- 无法确定 `master` 分支、合并策略或推送权限；
- 推送范围未确认，或无法判断是仅推送当前分支还是合并到 `master`；
- 存在多个远端、多个开发分支或多个项目；
- 工具默认 worktree 行为与实际状态不一致；
- 主工作区存在未提交改动，或目标 worktree 已存在且有改动；
- 推送命令、目标远端或合并顺序不明确；
- 合并到 `master` 出现冲突，或合并后构建/测试/校验失败；
- `master` 受保护、禁止直接推送，或需要绕过分支保护；
- 推送会触发自动部署、覆盖共享环境或影响他人；
- 需要 force push、改写历史、删除分支或删除 worktree；
- 缺少认证、权限、网络或工具版本不满足要求；
- 生成文件与手工修改混在一起，无法判断正确来源；
- 开发分支或 `master` 推送后核验失败、结果不一致。

## 用户确认方式

本 skill 中所有「等待用户确认」「询问用户」「先询问」的节点，都按本节执行。

需要用户确认时，优先使用当前会话提供的 Ask User Question / `request_user_input` 工具发起结构化提问：

- 每次只问当前阻塞推进的问题；多个独立问题可一次提出，但不超过 3 个。
- 每个问题提供 2–3 个互斥选项，推荐项放在第一位，并在选项标签末尾标注 `(Recommended)`。
- 问题正文包含：依据、影响、不确认的后果；每个选项说明选择后的实际影响，例如「复用现有 worktree」「新建 worktree」「停止」。
- 不要自行添加「其他」选项，客户端会自动提供自由输入。
- 如果 Ask User Question 工具在当前模式不可用，改用一条简短的纯文本问题，仍给出 A/B 选项与推荐项。
- 权限、审批或沙箱升级不要使用 Ask User Question，走当前环境的审批机制。
- 未获得用户回答前，不得创建 worktree、提交、推送、合并或执行其他受影响操作。

禁止用「我先假设……」绕过确认。

## 硬性约束

- 不在主工作区直接开发，不污染用户当前分支。
- 未确认推送范围前不得提交、推送或合并。
- 仅推送当前分支模式下，不得合并或推送 `master`。
- 开发阶段不向 `main`、`master`、`release` 等非开发分支推送；只有开发分支推送并核验成功后，才按第 6 步合并并推送 `master`。
- 不使用 `git push --force` 或等价操作。
- `master` 合并出现冲突或校验失败时不得继续推送，不得绕过分支保护。
- 不手工编辑工具生成的文件，除非工具文档明确允许。
- 不提交密钥、令牌、账号、个人配置、构建产物和临时文件。
- 不删除或重置用户已有 worktree、分支和未提交改动。
- 不把工具命令、分支名、远端名或推送参数写死；每次从项目实际配置中发现。
- 推送前必须校验，开发分支与 `master` 推送后都必须核验远端结果。
- 仅推送当前分支时，只有开发分支推送并核验成功后，才能输出「当前分支已推送」提示。
- 合并模式下，只有 `master` 合并、推送和核验全部成功后，才能输出「git仓库已同步」提示。
- 两种提示都必须使用引用块 + 粗体，只输出一次，任何一步失败都不得输出。
- 无法验证时如实说明，不得声称推送成功。

## 收到任务后的第一步

先执行参数发现，确认本次推送范围，再输出预检表。

如果工具、开发分支、`master` 分支、worktree 状态、推送范围、推送方式或合并策略不明确，先通过 Ask User Question（不可用时用纯文本）询问用户。

在预检通过并获得必要确认之前，不要创建 worktree、不要提交、不要推送。
